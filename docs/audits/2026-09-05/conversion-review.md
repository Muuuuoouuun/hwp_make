# 변환 안정성과 세부 오류 감사 — 2026-09-05

범위는 가져오기 → 문항 저장 → 미리보기/내보내기 → 결과 검증이다. 제품 코드와 기본 사용자 DB는 수정하지 않았다. API 재현은 `HWP_MAKE_DATA_DIR`를 새 임시 디렉터리로 지정한 뒤 앱을 import하여 실행했다. 프로젝트와 상위 관련 경로에서 적용할 AGENTS.md를 발견하지 못했다. 아래 P1/P2는 실제 중요도를 구분한 감사 우선순위이며 기존 자체 점수에 가산·감산하지 않았다.

## 핵심 판단

입력 검증, 동시 중복 삽입 방지, PDF 출력 구조 및 수식 기하 복원에 이미 회귀 방어가 있다. 그러나 **성공으로 보이면서 문항을 누락시키는 두 경로**가 현재 재현된다. 다음 개선은 외관 점수보다 문항 보존과 실패 복구를 먼저 고정해야 한다.

## 현재 재현되는 결함

### C1 · P1 · 대소문자만 다른 수학 문항을 중복으로 삭제

- 근거: `app/storage.py:230` 콘텐츠 해시, 특히 `:240`의 `.lower()`; `:360` 가져오기 내부 `seen` 검사와 `:393` 같은 출처 DB 검사; `app/importers.py:106` sink.
- 재현: 같은 CSV에 `number,stem / 1,Find f(x) / 2,Find f(X)`를 넣어 `/api/import` 호출. HTTP 200, 생성 문항은 1번 `Find f(x)` 하나이고 `중복 1개` 안내를 반환한다. 두 입력의 수학 의미는 다를 수 있다.
- 영향: 수학의 x/X, 점 A/a 등 실제 다른 문항이 사라지고 사용자는 정상적인 중복 제거로 이해하게 된다. 이것은 문서에 기록된 전 출처 중복 문제와 별개의 현재 결함이다.
- 개선: 원문 대소문자를 보존한 정확 중복 해시를 사용하고, 유사 중복 판단은 삭제하지 않는 별도 검토 상태로 표시한다. 해시 정책 변경 시 기존 데이터의 해시 재계산/버전 구분을 포함한다. 출처 식별을 파일명만으로 삼는 한계도 다음 단계에서 별도로 다룬다.
- 통과 조건: 같은 CSV의 x/X 두 문항 모두 보존; 동일 파일 재가져오기는 중복 생성 0; 다른 출처의 같은 문구는 보존; 해시 재계산 전후 기존 데이터 손실 0.

### C2 · P1 · 삭제되거나 없는 선택 문항을 조용히 빼고 내보내기 성공

- 근거: `app/storage.py:563`은 SQL `IN`으로 존재하는 ID만 반환한다. `app/main.py:1038` 내보내기 및 `:1012` 미리보기는 결과가 전부 비었을 때만 실패시킨다.

- 영향: 여러 탭, 이전에 복원한 선택 목록, 다른 작업에서 삭제된 문항이 섞인 경우 선택한 문제 수와 생성한 문제 수가 달라도 성공한다. 최종 시험지에서 문제 누락을 뒤늦게 발견하게 된다.

- 통과 조건: 유효 ID+없는 ID 혼합 요청은 409 또는 정의된 4xx와 누락 목록, 생성 파일 없음; 모두 유효한 요청은 선택 수·순서와 출력 inventory 일치; 모든 ID가 없는 경우에도 일관된 한국어 안내.

### C5 · P1 · 합본 자동 축약과 결과 검수 기준이 어긋남

`app/pdf_layout_writer.py:9917`부터 짝수 페이지 합본을 절반으로 나누어 첫 240자의 문제 stem과 번호를 비교한다. `:9957`에서 겹침 80% 이상/후반 번호 재시작이면 절반만 남기고, `:9983`, `:10113`, `:10484`에서 후반부를 제외한다. 이번 샘플의 overlap은 0.9783, variant_page_limit은 20이었다. 선지를 동일성 기준에 넣지 않으므로 홀수형/짝수형처럼 선지 순서가 다른 유형도 제거 대상이다.

그런데 `main.py:893`의 fidelity 비교는 원본 40쪽과 출력 20쪽으로 페이지 불일치를 기록한다. `:375`는 그 결과로 paging에서 60점을 감점한다. 현재 낮은 objective의 실제 구성은 layout 99.45, font/math 100, editable 99.24, balance 75, paging 40이다. 즉 **정책적으로 한 유형을 제거한 결과를 출력 누락처럼 감점**하는 상태다. API notices(`main.py:978`)도 이 자동 축약을 설명하지 않고 편집 가능한 텍스트/수식을 만들었다고만 안내한다.

- 영향: 사용자는 원본 40쪽이 20쪽이 된 이유와 낮은 점수의 의미를 동시에 오해할 수 있다. 합본 전체 보존을 기대했으면 의도하지 않은 범위 축소다. 겹침이 100%가 아닌 나머지 문항의 동일성/누락은 이번 감사에서 개별 대조하지 않았다.
- 개선: 가져올 유형/전체 합본 유지 옵션을 제공하고 적용한 페이지 범위·제외 문항 inventory를 명시한다. 사용자가 승인한 범위를 기준으로 fidelity를 비교하되 원본 전체 보존 여부를 별도 표시한다. 경고를 삭제하거나 점수 문턱만 낮춰서 해결하지 않는다.
- 통과 조건: 전체 보존 선택 시 40쪽/모든 유형 보존, 단일 유형 선택 시 사용자에게 1–20쪽 범위를 명확히 고지; 선택 범위 내 누락 0; 범위 축약이 뜻하지 않은 페이지 불일치와 섞이지 않음; 선지가 다른 유형을 같은 콘텐츠로 오판하지 않음.

### C6 · P2 · ‘수식 높이 부족 1,009’로 기록된 실패의 실제 종류가 다름

`scripts/verify_native_math_layout_heights.py:370`은 높이가 1000을 넘는 모든 picture에 inline 배치를 요구하고, `:383`에서 `figure_not_safe_inline`을 쌓는다. `app/pdf_layout_writer.py:10371`의 고충실도 수학 출력은 의도적으로 좌표 그림을 겹쳐 올리므로 이 요구와 충돌한다. 이번 1,009건은 모두 이 종류이며 native 수식 281개의 문단/셀 높이 부족은 0이다.

- 판단: **1,009개의 수식이 잘렸다는 증거가 아니다.** 현재 산출물이 그 검사에 실패한다는 사실과, 검사 계약이 해당 출력 모드에 맞는지 문제를 분리해야 한다. 실제 한글 편집 후 재배치 안전성은 여전히 별도 검증 대상이다.
- 개선: 순수 reflow/좌표 overlay 모드별 oracle을 분리한다. reflow에는 inline height와 flow 충돌 검사를 유지하고 좌표 모드에는 bounding box, overlay 순서, 수식 editability 및 편집 후 이동 검사를 둔다. 문서에서 ‘수식 높이 부족’ 대신 실패 종류별 수를 기록한다.
- 통과 조건: paragraph/cell shortage와 그림 배치 경고의 집계가 분리됨; 의도한 좌표 그림을 무조건 불합격시키지 않되 실제 겹침/잘림 fixture는 계속 검출; 이 실물 샘플을 생성부터 검사까지 자동 관문에 포함한다.

위 두 항목은 과거 낮은 평가를 ‘아직 수식 1,009개가 깨졌다’로 재사용하지 말아야 하는 근거다. 동시에 91.3점 산출물을 출시 품질로 승격한다는 의미도 아니다. 자동 축약 정책과 최종 편집/렌더 검증이 해결되어야 한다.

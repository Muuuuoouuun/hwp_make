# UI 코드·사용자 경로 감사

검토일: 2026-09-05. 범위: `static/index.html`, `static/app.js`, `static/styles.css`, 화면이 호출하는 `app/main.py` API. 제품 코드는 변경하지 않았다. 루트·상위 경로 및 저장소 파일 목록에서 적용할 AGENTS.md는 발견되지 않았다. 이 문서의 발견 사항은 코드 추적에 근거하며, 브라우저 관찰은 별도 담당자의 결과와 합쳐야 한다. 실제 렌더 품질·사용자 평가 점수는 이 검토에서 측정하지 않았다.

## 판단

기본 화면은 파일 선택 → 변환 → 최근 파일이라는 짧은 경로를 갖추었다. 스튜디오는 자동 저장, 단계 이동, 반응형 패널, 실제 미리보기, 순서 편집을 갖추고 있다. 그러나 두 화면이 같은 DOM·전역 상태·명령을 공유하면서 **실패 원인을 숨기고, 결과와 다음 행동을 연결하지 못하며, 변환 중 선택 상태를 바꿀 수 있는 문제**가 남았다. 다음 개선의 중심은 장식보다 상태 정합성, 실패 복구, 품질 증거의 정확한 표시여야 한다.

P1은 핵심 작업 실패·사용자 데이터 손실 가능성·결과 오인을 먼저 차단할 항목, P2는 경로·설명·복구의 마찰을 줄일 항목이다.

## 우선 발견 사항

### UI-01 · P1 · 간단 변환의 상세 오류와 중요 안내가 숨겨짐

- 근거: `static/styles.css:661`–664에서 간단 모드의 모든 `.toast`를 `display:none!important`로 숨긴다. `static/app.js:2442`–2471 및 2536–2559는 상세 실패를 toast에 출력하고 `false`를 반환한다. `static/app.js:3429`–3433은 이 반환값을 일반적인 “파일을 확인한 뒤 다시 시도” 문구로 바꾼다. import의 notices도 2432–2437의 toast에만 담긴다.
- 재현: 간단 모드에서 확장자만 PDF인 잘못된 파일, 손상 문서, 서버 오류를 발생시키면 된다. PDF API는 `app/main.py:815`–816에서 구체적인 오류를 제공하지만 최종 화면은 이를 유지하지 않는다.
- 영향: 파일 문제·서버 연결·지원 기능·이미 반영된 부분 결과를 구별하지 못하고 같은 파일 재시도만 반복한다. 화면 낭독기도 `display:none`인 상세 메시지를 읽을 수 없다.
- 개선: 작업 결과를 `{status, errorCode, message, recovery, artifacts, warnings}`로 반환하고 간단 화면에 지속적으로 표시한다. 상세 메시지는 toast가 없어도 읽을 수 있어야 한다. 실패 원인에 맞는 파일 교체·재시도·기록 확인 동작을 제공한다.
- 수용 기준: 400/413/500/네트워크 단절/부분 성공/취소 각각에서 원인과 다음 행동이 현재 화면에 남고, 새 작업 전까지 사라지지 않는다. 서버의 구체적인 원인이 일반 문구로 덮이지 않는다.

### UI-02 · P1 · 진행 중에도 마우스로 파일을 교체할 수 있음

- 근거: `static/index.html:40`의 업로드 영역은 file input과 연결된 label이다. `static/app.js:3398`은 label에 `aria-disabled`만 설정한다. `static/styles.css:754`는 커서·불투명도만 바꾼다. keyboard/drop에는 busy 검사가 있지만 `static/app.js:3623`–3624의 input change에는 없다. 파일 input의 `disabled` 설정도 없다.
- 재현: A 파일 변환 중 업로드 영역을 마우스로 클릭해 B 파일을 선택한다. B 이름과 “준비되었습니다”가 표시되고 `setSimpleFile`의 3274가 변환 버튼을 다시 활성화할 수 있다. 실제 실행은 기존 A를 계속 처리한다.
- 영향: 보이는 파일과 처리 대상이 달라지고 완료·점수가 B 결과인 것처럼 보인다. 버튼은 활성화되어도 `runSimpleConversion` busy guard 때문에 반응하지 않는다.
- 개선: 진행 중 file input과 선택 UI를 실제 비활성화하거나, 다음 작업 대기열을 명시적으로 분리한다. 작업 객체에 입력 파일 스냅샷과 결과 연결을 저장한다.
- 수용 기준: 진행 중 마우스·키보드·drop 어떤 경로로도 현재 작업의 선택 표시가 바뀌지 않으며, 완료 카드에 실제 변환한 파일명이 표시된다. 완료 후 새 선택 시 이전 점수도 제거된다.

### UI-03 · P1 · 간단 모드에서 스튜디오 단축키가 숨겨진 UI를 동작시킴

- 근거: `static/app.js:915`의 전역 핸들러에는 화면 모드 분기가 없다. Ctrl+O는 908–912와 983–987을 통해 스튜디오 file input을 연다. `?`는 1008–1011에서 도움말 모달을 연다. 832–841은 `.hidden` 클래스 여부만으로 모달 열림을 판단해 스크롤을 잠그지만, 간단 모드 모달은 `static/styles.css:663`–664에서 계속 숨긴다. `static/styles.css:31`은 modal-open일 때 스크롤을 막는다.
- 재현: 간단 화면에서 Ctrl+O로 파일을 고른 뒤 선택 표시를 확인한다. `?`를 눌러 도움말 표시·스크롤 상태를 확인한다. Ctrl+Enter도 스튜디오 basket이 있으면 숨겨진 미리보기를 실행할 수 있다.
- 영향: 사용자가 고른 파일이 화면에 나타나지 않는다. 보이지 않는 모달 상태가 생기며 스크롤·후속 단축키가 비정상 작동한다.
- 개선: 단축키를 현재 화면의 명령에 연결한다. 모달 상태는 실제 활성 화면에서만 생성하고, 공통 모달을 쓰려면 간단 화면에서도 표시·배경 inert·초점 복원이 일관되게 작동하도록 한다.
- 수용 기준: 간단 모드 Ctrl+O는 간단 파일 선택을 갱신한다. `?`는 보이는 도움말을 열거나 처리하지 않는다. 모드를 바꿔도 숨겨진 모달 때문에 키보드·스크롤이 막히지 않는다.

### UI-04 · P1 · 품질 점수가 검수 완료처럼 보이지만 경고·미검증 범위가 표시되지 않음

- 근거: `static/app.js:3291`–3305는 objective score와 목표만 출력한다. API의 `app/main.py:916`–932에는 편집 가능 비율, 시각 검수 플래그, 전체 페이지 이미지 fallback, 페이지 제한, 수동 검수 필요 상태가 있다. 879–888의 일반 structured 분기는 시각 일치 검사를 생략한다. 이 정보와 `run.report`(970–972)를 UI가 사용하지 않는다. 2524–2530에서 점수·경고 표시보다 다운로드를 먼저 시작한다.
- 재현: structured PDF, full-page image fallback, 목표 미달 결과의 품질 표시를 비교한다. 모두 같은 문장 형태의 “변환 품질 n점 · 목표 n점”으로 요약된다.
- 영향: 내부 합성 점수를 실제 한글 열림·원본 일치·완전 편집 가능성의 종합 보증처럼 받아들일 수 있다. 낮은 점수의 이유를 알거나 해당 부분을 검수할 수 없다.
- 개선: “파일 생성 완료”와 “검수 필요”를 분리한다. 확인한 항목·아직 확인하지 않은 항목을 표시하고, fallback·누락·목표 미달을 행동 가능한 경고로 올린다. 점수에는 계산 범위 설명과 상세 보고서·문제 페이지 링크를 연결한다.
- 수용 기준: 시각 검사를 수행하지 않은 결과는 “시각 일치 미검증”이 보인다. 전체 페이지 이미지 fallback은 편집 제한이 보인다. 임계값 미달 결과는 경고와 검수 경로가 있으며 단순 성공 상태만 표시하지 않는다.

### UI-05 · P2 · “스튜디오에서 세부 검수·편집”이 변환 결과를 열지 않음

- 근거: PDF 간단 변환은 `static/app.js:3407`–3412의 `/api/pdf-layout-export` 경로다. `app/main.py:965`–983의 응답은 산출 파일·통계·보고서이며 studio 문제 id가 없다. `static/app.js:3348`–3377의 `applyUiMode`는 모드와 패널 크기만 바꾼다. 그러나 3305의 품질 안내는 스튜디오 검수·편집을 약속한다.
- 재현: 새 세션에서 PDF 변환 완료 후 “스튜디오에서 자세히 편집”을 누른다. 변환한 결과가 자동으로 열리거나 해당 보고서에 연결되는 코드가 없다. 기존 세션이면 이전 basket·문항이 그대로 나타난다.
- 영향: 성공 직후 사용자의 다음 행동이 끊긴다. 다른 시험지가 나타나면 방금 변환한 문서로 착각할 수 있다.
- 개선: 완료 결과별 “결과 검수”를 제공해 생성 HWPX, 원본 PDF, 품질 보고서를 동일 작업으로 연다. 스튜디오에서 재가져오기가 필요하면 그 단계를 명시한다. 직접 연결을 만들기 전까지 문구를 “변환 파일을 내려받아 한글에서 편집” 등 실제 가능한 경로와 맞춘다.
- 수용 기준: 완료 카드의 검수·편집 동작 한 번으로 같은 결과가 식별되어 열리며, 원본 파일명과 작업 id가 유지된다. 이전 basket을 결과로 오인하지 않는다.

### UI-06 · P1 검증 후보 · 비동기 목록 새로고침 중 추가 입력이 덮일 수 있음

- 근거: `static/app.js:3599`–3602는 검색 전에 draft를 저장하지만, 그 뒤 목록 GET이 진행되는 동안 에디터 입력은 열려 있다. 응답 시 `loadProblems`의 372–375는 `renderEditor()`를 호출한다. `renderEditor`는 2077–2086에서 필드를 서버 값으로 다시 대입하고 2108에서 draftDirty를 false로 만든다. 저장 직렬화의 revision 보호(2154 이후)는 목록 응답의 필드 덮어쓰기까지 막지 않는다. 이미지 첨부·삭제의 `loadProblems()` 경로(2242,2267)도 같은 구조다.
- 재현 조건: 검색을 실행해 GET을 지연시키고, 응답 전에 현재 문항에 새 문장을 입력한다. 900ms 자동 저장 이전에 GET이 도착하도록 한다. 새 문장이 사라지는지 확인한다. 이미지 업로드 대기 중 입력도 후보이다.
- 영향: 편집 중 입력이 사라지고 dirty도 해제되면 재시도나 이탈 경고가 남지 않는다. 실제 브라우저 지연 재현이 필요한 후보이며 이 문서에서는 데이터 손실을 실측했다고 주장하지 않는다.
- 개선: 목록 응답이 에디터를 무조건 다시 렌더링하지 않게 분리하고, 문제별 draft와 revision을 보관한다. 에디터를 갱신할 때 요청 당시 revision과 최신 revision을 비교한다.
- 수용 기준: 2초 GET/이미지 업로드 지연 중 추가 입력이 모두 유지되고, 저장 요청의 마지막 payload가 그 입력을 포함한다. 검색 실패·새로고침 성공 여부와 무관하게 미저장 draft가 보존된다.

### UI-07 · P2 · 취소·장기 처리의 의미와 복구가 부족함

- 근거: `static/app.js:3650`–3653은 fetch AbortController를 취소하고 3426–3427에서 “변환을 취소했습니다”로 표시한다. `app/main.py:807`의 동기 변환 핸들러에는 작업 id·취소 상태·disconnect 확인이 없고, _EXPORT_LOCK 아래의 변환을 계속 수행할 수 있다. `static/app.js:3799`–3802의 이탈 보호도 draft에만 적용된다.
- 재현 조건: 큰 PDF 변환 중 취소하거나 페이지를 다시 연다. 서버 측 변환이 끝난 뒤 exports에 결과가 생기는지 별도 확인한다.
- 영향: 사용자에게는 취소 완료지만 서버에는 작업/파일이 남을 수 있다. 재접속한 화면은 진행 중 작업을 찾을 수 없고, 재시도하면 또 변환하게 된다.
- 개선: 서버 job id를 저장하고 업로드·대기·변환·검수·완료·실패·취소 요청 상태를 분리한다. 작업 중단이 불가능한 단계에서는 “화면의 대기를 중단했습니다. 생성 중인 결과는 최근 변환에서 확인하세요”처럼 실제 의미를 전달한다.
- 수용 기준: 취소 후 파일이 생성되면 해당 작업의 최종 상태·결과를 찾을 수 있다. 새로고침 후 진행 중 작업을 복구할 수 있고 동일 작업이 무심코 중복 실행되지 않는다.

### UI-08 · P2 · 최근 변환 실패에 “다시 시도”가 없고 결과 선택과 점수 수명이 분리됨

- 근거: `static/app.js:3317`–3319는 최근 변환 로드 실패 시 “잠시 후 다시 시도” 텍스트만 출력한다. 스튜디오에는 1888–1893의 실제 다시 시도 버튼이 있다. `setSimpleFile`(3252–3282)은 파일 교체·제거 시 품질 문구를 지우지 않고, `setSimpleQualityNote("")`는 새 실행 3401에서만 호출한다.
- 재현: 기록 API 실패 후 서버가 복구되어도 간단 화면에 갱신 버튼이 없다. A 변환 완료 뒤 B 선택 또는 A 제거 시 A 품질 점수가 그대로 남는다.
- 개선: 이력 재시도 버튼, 결과별 영구 다운로드·검수 버튼을 제공한다. 품질은 현재 선택 영역이 아니라 해당 완료 결과 카드에 귀속한다.
- 수용 기준: 새로고침이나 모드 변경 없이 기록을 복구한다. 파일 선택·제거 후 이전 결과 점수가 새 입력의 점수처럼 보이지 않는다.

### UI-09 · P2 · 비활성 AI 옵션의 설정 경로가 기본 화면에서 드러나지 않음

- 근거: `static/index.html:66`–69의 체크박스는 disabled이고 설정 안내는 title에만 있다. `static/app.js:2943`–2951도 title만 갱신한다. 기본 화면에는 AI 설정 버튼이 없으며 설정 modal은 CSS로 숨겨진다. PDF 여부에 따라 옵션을 숨기거나 바꾸는 연결도 없다.
- 재현: Gemini 미설정 상태의 기본 화면에서 키보드·터치로 AI 사용 가능 조건을 알아내려 한다. 설정된 상태에서도 TXT 파일에 PDF 전용 옵션이 계속 표시된다.
- 개선: PDF 선택 시에만 관련 옵션을 표시하고 “AI 연결 설정”을 인접 동작으로 제공한다. 비활성 사유는 hover title 대신 화면에 보이는 설명과 aria-describedby로 제공한다.
- 수용 기준: 키보드와 터치로 AI 비활성 이유·설정 경로를 확인할 수 있다. TXT 등에는 적용되지 않는 PDF 옵션이 나타나지 않는다.

### UI-10 · P2 · 작업 미리보기와 최종 출력의 차이를 시각적으로 알 수 없음

- 근거: `static/index.html:381`의 “화면은 ... 작업 미리보기” 안내는 visually-hidden이다. `static/app.js:1614`–1617은 페이지 배치가 추정임을 명시하지만 사용자 화면은 “시험지 미리보기”다. 실제 미리보기와 DOCX가 다른 기준인 점은 2864–2889에서 실제 요청 후에야 안내된다.
- 재현: 스튜디오 캔버스에서 페이지·단·수식 배치를 확인하고 그대로 출력될 것으로 기대한다. DOCX를 고른 뒤 실제 미리보기를 누른다.
- 개선: 캔버스 헤더에 “구성 미리보기 · 페이지 배치는 출력과 다를 수 있음”을 보이게 한다. 실제 버튼은 선택 형식과 검증 범위가 드러나게 한다. 가능하면 최종 결과 artifact의 렌더를 그대로 재사용한다.
- 수용 기준: 처음 사용하는 사람이 버튼을 누르기 전 두 미리보기의 차이를 확인할 수 있다. DOCX 선택 시 HWPX 기준이라는 설명이 클릭 전에도 보인다.

### UI-11 · P1 · 삭제된 문항이 바구니에 남고 일부만 출력되어도 전체 성공으로 표시됨

- 근거: `static/app.js:1404`–1420은 origin 단위 localStorage에서 id·label을 복구한다. `hydrateBasketProblems`의 2209–2213은 404 등 rejected 결과를 무시하며 항목을 제거하거나 미확인 표시하지 않는다. `renderBasket`의 1694–1703은 유효 id 수가 아닌 basket.length로 개수·출력 가능 상태를 결정한다. `app/storage.py:563`–575는 조회에 성공한 id만 반환한다. `app/main.py:1040`–1042와 1016–1018은 결과가 완전히 비었는지만 검사한다. 성공 안내 `static/app.js:2729`는 실제 출력 수가 아닌 요청 ids.length를 사용한다.
- 관찰: root가 기존 origin의 localStorage 바구니 3개와 격리된 빈 DB를 함께 사용한 화면에서 “가져온 0 / 담은 3”, export 활성화를 직접 확인했다. 별도 변환 담당 agent가 유효 id + 없는 id의 export 요청에 HTTP 200으로 일부 문항만 출력되는 동작을 재현했다. 이 API 재현의 세부 기록은 동일 감사 폴더의 변환 보고서와 함께 확인한다.
- 일반 재현: A 탭에서 담은 문항을 B 탭에서 삭제한 뒤 A에서 새로고침 또는 출력한다. 전부 삭제되면 유령 문항을 표시하며 출력 시에야 오류가 난다. 일부만 삭제되면 조용히 빠진 시험지를 성공으로 출력할 수 있다.
- 영향: 시험지 문항 누락과 잘못된 성공 수량이다. DB를 교체했을 때 같은 숫자 id가 다른 문항으로 재사용되는 경우에는 오래된 선택이 다른 내용으로 연결될 위험도 있다.
- 개선: 복구된 바구니는 유효성 검사 완료 전 출력 준비로 표시하지 않는다. 404는 “삭제된 문항”, 네트워크 실패는 “확인 필요”로 구분한다. 서버 export/preview는 요청 id 전체가 존재하는지 검사해 누락 id를 반환하고 조용한 부분 출력을 막는다. 저장 바구니는 DB/작업공간 식별자를 함께 보관한다.
- 수용 기준: 일부 id 누락 요청은 명시적 오류와 누락 목록을 반환한다. UI 수량과 실제 산출 문항 수가 항상 같고, 유효성을 확인하지 못한 바구니는 출력 전 해결 경로를 보여준다. 다른 탭 삭제 및 DB 초기화·교체 시나리오에서 잘못된 문항이 출력되지 않는다.

## 기존 검증의 의미

실행 결과:

- `node scripts/verify_frontend_simple_converter.js`: 통과 (`Frontend simple converter contracts OK`).
- `node scripts/verify_frontend_accessibility.js`: 통과 (`Frontend accessibility + conversion trust contracts OK`).

두 검증은 소스 문자열·정규식 기반 계약 확인이다. 예를 들어 취소 문구와 abort 호출, 접근성 속성이 있는지는 검사하지만 실제 표시 여부, 파일 입력의 마우스 활성화, 숨겨진 단축키, 네트워크 응답 순서, 화면 낭독기 결과는 검사하지 않는다. 따라서 통과 결과는 위 UX 결함을 반증하지 않는다. 현재 낮은 평가 세부 사항을 막는 데에는 소스 토큰 추가보다 행동 검증이 필요하다.

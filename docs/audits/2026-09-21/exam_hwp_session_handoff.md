## 먼저 알아야 할 결론

1. 공개 편집용 HWPX 4종은 현재 가져오기에서 각각 **한 문항으로 합쳐진다**. 미주 해설 일부가 문제 본문에 섞이고, 정답·해설 필드는 비어 있다. 자작 3문항 예제로도 재현했다.
2. **원본의 `endNote/@instId`도 고유 ID라고 믿을 수 없다.** 공개 수학 46개·영어 45개·지구과학 20개의 미주가 각각 모두 `instId=1`이다. 국어도 `instId=1`이 11번 반복된다.
3. 해설은 일반 텍스트만이 아니다. 공개 수학의 수식 1,696개 중 **1,205개**, 그림 18개 중 **10개**가 미주 내부에 있다. 미주 텍스트만 따로 빼는 수정으로는 해설 개체가 보존되지 않는다.
4. 문단 번호와 미주는 동시에 존재할 수 있다. 배포자는 문단 번호 뒤에 **1pt 흰색 미주 번호를 넣어 답안 연결을 유지하는 방식**을 설명한다. 이번 4개 표본은 그 방식이 아니므로, 별도의 지원 사례로 추가해야 한다.
5. 한글 직접 편집은 아직 미검증이다. 사용자 요청으로 Computer Use를 재시도했고 **Windows 잠금 화면**을 확인했다. 잠금 해제 후 파일 열기부터 재개해야 한다.

## 추가 실물 계측

새 도구: [inspect_exam_hwpx_semantics.py](../../../scripts/inspect_exam_hwpx_semantics.py). 원시 결과: [semantic_inventory.json](../../../data/research/20260921_hwp_exam/semantic_inventory.json). 본문과 해설 문장은 출력하지 않고 ID·스타일·개체 개수만 기록했다.

추가 도구는 구문·Ruff 검사를 통과했다. 5개 파일의 SHA-256, 원시 XML의 미주/고유 ID 개수, 기존 구조 계측과 개체 합계도 대조했다. 결과는 `data/research/20260921_hwp_exam/semantic_inventory_validation.json`에 있다. 이 검증은 연구 계측의 일관성을 확인하며 변환 품질이나 한컴 GUI 합격을 부여하지 않는다.

### 미주 ID 중복

| 공개 파일 | 미주 수 | 서로 다른 `instId` | 실제 중복 |
| --- | ---: | ---: | --- |
| 영어 | 45 | 1 | `1`이 45회 |
| 수학 | 46 | 1 | `1`이 46회 |
| 국어 화작 | 45 | 35 | `1`이 11회 |
| 지구과학Ⅰ | 20 | 1 | `1`이 20회 |

이는 현재 importer가 ID 딕셔너리를 사용한다는 뜻이 아니다. **새로 연결 처리를 구현할 때의 데이터 손실 위험**이다. `instId` 하나를 키로 만든 맵은 이 표본의 서로 다른 미주를 합칠 수 있다.

설계 제안: 원본 위치는 `(문서 SHA-256, section XML 경로, 원본 제어 요소 위치)`로 기록하고, 편집·재배열 뒤에도 유지될 내부 ID는 별도로 발급한다. 위치 정보는 해당 원본 스냅샷의 출처이며 재배열 후의 영구 식별자와 같지 않다. 원본 번호·현재 표시 번호·연결 ID도 분리한다.

### 문제 영역과 미주 영역의 개체 수

아래 값은 미주 내부 / 미주 외부다. ‘미주 외부’에는 전체 section 트리에서 미주를 제외한 다른 컨테이너도 포함되므로 순수 문제 본문과 항상 같지는 않다.

| 공개 파일 | 수식 | 표 | 그림 |
| --- | ---: | ---: | ---: |
| 영어 | 9 / 12 | 2 / 13 | 0 / 3 |
| 수학 | 1,205 / 491 | 4 / 34 | 10 / 8 |
| 국어 화작 | 14 / 53 | 0 / 23 | 0 / 5 |
| 지구과학Ⅰ | 274 / 227 | 0 / 45 | 1 / 17 |

네 파일의 미주 모두 `sec/p/run/ctrl/endNote` 구조에 있다. 최상위 본문 문단의 heading type은 모두 `NONE`이고 별도 numbering 정의는 없다. 미주를 담은 run의 저장 글자 속성은 모두 높이 900, 검정색이다. 이는 실제 표시 크기나 위 첨자 적용을 실측한 결과가 아니다.

공개 국어에는 `pageBreak=CELL`이면서 `treatAsChar=1`인 표도 하나 있다. 속성 하나만 보고 ‘자동 여러 쪽 지원’으로 판정하지 말아야 할 실제 사례다. 이것만으로 해당 표가 현재 잘려 있다고 판정하지는 않는다.

## 웹에서 추가 확인한 실제 편집 조건

### 보이는 번호와 해설 연결 번호가 다를 수 있다

제작자의 [2026-03-18 서식 설정 안내](https://www.my1ta.com/blog/release-hwp-format-preset)는 미주 번호 방식과 문단 번호 방식을 모두 제공하며, 후자는 문단 번호 뒤에 작은 흰색 미주 번호를 붙여 답안 연결을 유지한다고 설명한다. 이 설명의 ‘사설모의고사 표준’이라는 표현은 제작자의 주장이고, 여기서는 해당 작성 방식이 존재한다는 근거로만 사용한다.

따라서 보이는 글자·색상·크기로 문항 경계를 추정하는 처리와, 문서 제어 요소의 연결을 읽는 처리는 구분해야 한다. 흰색이나 작은 글자라는 이유로 미주 앵커까지 제거하면 연결이 사라질 수 있다. 이번 공개 4종은 문단 번호 방식 표본이 아니므로 이 경우를 검증했다고 말하지 않는다.

한글의 [문단 시작 번호 방식](https://help.hancom.com/hoffice130/ko-KR/Hwp/format/numberbullet/numberbullet%28new_number%29.htm)은 앞 목록에 이어가기, 새 번호 시작, 이전 목록에 이어가기를 구분한다. [미주 모양](https://help.hancom.com/hoffice130/ko-KR/Hwp/insert/annotations/endnote_format.htm)도 구역별 재시작과 이전 구역에서 이어가기를 지원한다. 같은 문서에서 표시 번호가 반복돼도 곧바로 중복 문항으로 제거하면 안 된다.

### 글상자 자동 높이와 여러 쪽 흐름은 다른 기능이다

한글 2024의 [글상자 크기 조절](https://help.hancom.com/hoffice130/ko-KR/Hwp/insert/textbox/textbox%28size%29.htm)은 크기를 고정하면 세로 범위를 넘는 내용이 보이지 않는다고 설명한다. 따라서 자동 높이 검사는 ‘크기 고정 해제’, 실제 내용 높이, 저장 후 화면·인쇄 결과를 함께 봐야 한다.

[글상자 연결](https://help.hancom.com/hoffice130/ko-KR/Hwp/insert/textbox/textbox%28textlink%29.htm)은 넘친 글을 다른 글상자로 이어 주는 별도 기능이다. 이것이 있다는 사실을 현재 프로젝트의 문항 글상자 구조를 바꾸는 근거로 삼지는 않는다. 긴 문항 처리 정책은 수신 세션의 최신 사용자 요구를 유지하면서 결정해야 한다.

### 표를 글자처럼 취급하면 여러 쪽 분할 조건이 달라진다

[여러 쪽 지원](https://help.hancom.com/hoffice130/ko-KR/Hwp/table/tableattribute/table%28many%29.htm)에 따르면 글자처럼 취급한 표에는 여러 쪽 지원 설정이 효력을 갖지 않으며, 한 쪽보다 큰 표의 넘친 내용은 화면과 인쇄에 나타나지 않을 수 있다. 이는 일반 한글 표의 공식 설명이며, 생성 문항 글상자 안의 중첩 표에 대한 실험 완료를 의미하지 않는다.

후속 검증은 `pageBreak` 값뿐 아니라 `treatAsChar`, 조상 글상자, 셀 내용 높이, 쪽의 가용 높이를 함께 다뤄야 한다. 작은 표는 정상이어도 글을 늘린 뒤 한계를 넘을 수 있다.

### 조판 부호 동반 이동에도 적용 조건이 있다

[위치 도움말](https://help.hancom.com/hoffice130/ko-KR/Hwp/table/tableattribute/table%28position%29.htm)은 ‘개체와 조판 부호를 항상 같은 쪽에 놓기’가 **자리 차지**에 적용되며, 어울림·글 앞으로·글 뒤로에는 효력이 없다고 설명한다. [본문과의 배치](https://help.hancom.com/hoffice130/ko-KR/Hwp/table/tableattribute/table%28arrange%29.htm)는 글자처럼 취급 상태에서는 본문 배치 설정이 효력을 갖지 않는다고 설명한다.

그러므로 앵커 관련 플래그 하나로 문항 소속과 편집 후 이동을 보장했다고 판정할 수 없다. 실제 문항 앞에 내용을 추가해 그림 위치·조판 부호·문항 ID의 대응을 확인해야 한다.

### 공동지문은 별도 관계로 보존해야 한다

제작자의 [타이핑 가이드](https://www.my1ta.com/guide/hangeul-typing)는 제시문·참고자료·보기와 연결 문항을 함께 다루고 공통 지문 문항을 묶어 처리하도록 안내한다. [교재 편집 가이드](https://www.my1ta.com/blog/guide-hwp-editing-basics-document-structure)는 편집된 문항을 사용자의 판형·머리말·번호·해설 형식에 맞춰 재구성하는 작업을 설명한다.

설계 제안: 공동지문을 특정 문항의 앞부분으로 무조건 합치지 말고 연결 문항 ID를 보존한다. 여러 문항을 이동할 때는 지문을 한 번만 동반하고, 한 문항을 발췌할 때는 지문 포함 여부를 명시적으로 다룬다. 이를 이번에 구현하거나 UI 실험한 것은 아니다.

공개 4종 실패의 직접 실행 범위는 **HWPX importer**다. HWP 경로는 코드와 IR 구조를 확인했으며 같은 결과를 실행 검증했다고 확대하지 않는다. 표·수식·그림의 해설 소속 손실 가능성도 수정 후 별도 개체 대조가 필요하다.

실패 실행 당시 `app/importers.py`와 `app/storage.py` 해시는 추가 조사 중에도 동일함을 확인했다. 수신 세션은 이후 변경 여부를 다시 확인하고 해당 시점 코드에서 재현해야 한다.

## 수신 세션의 현재 작업과 연결

수신 세션의 [최신 문단 서식 평가](native-paragraph-format-progress.md)는 조사 시점에 배치 평균 69.09, 85 PASS / 11 SKIP / 2 FAIL, 한컴 직접 편집 미검증을 기록하고 있었다. 이 수치는 **수신 세션의 별도 검사 결과**이며 이 연구가 재검증한 것은 아니다. 1차 연구의 `generated_math.hwpx`는 이전 `native_final_v2` 사본이므로 최신 배치 개선 결과와 혼동하지 않는다.

이 인계로 현재 수학 배치·선택지·들여쓰기 작업의 우선순위를 임의로 바꾸지는 않는다. 가져오기 문제는 별도 재현 가능한 과제로 등록하고, GUI 편집 검증을 재개할 때 글상자·표·앵커의 적용 조건을 함께 확인한다. 수신 세션의 최신 사용자 지시와 승인된 문서 구조를 우선한다.

GUI 재개 조건은 **사용자의 직접 Windows 잠금 해제**다. 창 목록과 화면을 새로 관찰하고 실험용 사본부터 연다. 잠금 상태를 우회하지 않으며, 구조 검사나 자체 렌더 통과를 한컴 편집 통과로 기록하지 않는다.

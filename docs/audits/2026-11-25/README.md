## 찾은 것과 고친 것

### 인식 (`app/recognition/pdf_segment.py`, `pipeline.py`)

1. **자료 상자 안 글 소실 (본문의 31.8%)**. 영어 밖 과목은 그림 영역 안의 줄을 모두 "그림 라벨"로 보고 본문에서 뺐다. 그런데 글자가 24자 이상인 영역은 그림으로도 자르지 않아, 보기·제시문 상자의 글이 글로도 그림으로도 남지 않았다. 예: 생활과 윤리 1번 "(가), (나) 윤리학의 핵심 과제로…"에서 (가)·(나) 제시문이 통째로 없었다.
   고친 방법: 영역을 이미지로 자를지 정하는 판정 하나(`figure_is_crop_candidate`)가 "본문에서 뺄 줄"도 함께 정한다. 줄을 본문에서 빼도 되는 것은 그 줄이 잘라 낸 그림 안에 남을 때뿐이다. 그림인지는 상자 안에 테두리 말고 그려진 것이 있는가로 본다(`_figure_has_graphics`): 래스터 그림이 면적의 8% 이상, 안쪽 세로선 길이 합이 높이의 절반 이상, 안쪽 도형 면적이 15% 이상 중 하나. 밑줄·빈칸인 가로선은 증거로 쓰지 않는다. 영어는 기존 규칙 그대로다.
2. **공통 지문 미연결 (7.9%)**. 같은 쪽의 `[N~M]` 지문을 문항에 연결하는 처리가 영어에만 있었다. 전 과목으로 넓히고, 영어 밖에서는 줄 맨 앞의 머리만 인정한다(수식의 구간 표기 `[1-3]`과 구분). 범위의 모든 문항이 지문 사본을 갖는다(영어의 기존 설계와 같다).
3. **한쪽 단에만 문항이 있는 쪽의 1단 오판**. 국어 문항 쪽 157개 중 48개가 "왼쪽 단은 지문, 오른쪽 단만 문항" 구조인데 1단으로 판정되어, 반대편 지문 58,934자가 높이순으로 문항 본문에 섞였다. 쪽 중앙의 세로 구분선이 있고 본문 줄이 가운데를 가로지르지 않으면 2단으로 본다.
4. **쪽을 넘은 지문**. 앞 쪽에서 문항 없이 쪽 끝까지 이어진 지문(열린 지문)의 뒷부분을 다음 쪽 선두에서 이어 붙인다. 읽기 순서상 바로 다음 문항이 범위의 시작 번호일 때만 연결한다.
5. 그 밖: 번호 줄이 120자에서 잘리던 것, 1~5번 문항의 번호 줄이 숫자형 선지로 오인되어 문항 박스가 일찍 잘리던 것, 본문의 "10. 3. 1. 운동…", "11. 오전 9시…" 같은 문항 줄이 인쇄일로 버려지던 것, 전각 대괄호 `［N～M］` 지문 머리, 한 경로로 그린 표.

### 적용 (`app/pdf_native_content.py`, `pdf_question_inspection.py`, `pdf_layout_writer.py`, `importers.py`)

1. **번호 없는 쪽이 변환 전체를 실패시킴**. 표지나 "이 면은 여백입니다" 쪽은 인식이 번호 0 보존 항목으로 만드는데, 편집형 작성기가 이것을 "있어야 할 문항"으로 세어 `ValueError`로 끝났다. 인벤토리에서 번호 0을 뺀다. 그 쪽의 글은 일반 문단으로 남는다.
2. **"Gemini 수식 인식" 체크박스**. 켜도 Gemini를 부르지 않았다(구 작성 경로 570줄에 수식 AI 참조 0건, 실행해서 네트워크 시도 0회 확인). 수학 시험지에서 출력만 구형 작성기로 바뀌어 지표가 나빠졌다(미해결 자리표시 0 → 1, 편집 텍스트 보존 1.0 → 0.992). 모든 요청이 네이티브 작성기를 쓰게 하고, 요청 시 "아직 연결되어 있지 않다"는 안내를 붙였다.
3. **`<보기>`의 a./b. 항목이 선지로 오인됨**. 상자 글이 본문에 들어오자 제2외국어에서 선지가 8~9개인 문항이 30건 생겼다. 원문자 선지 묶음(①②③…)이 있는 문항의 글자 라벨 줄은 보기 항목으로 본문에 남긴다.
4. 지문 사본의 글자별 좌표가 문항마다 복제되어 레이아웃 저장량이 41.9MB → 77.1MB로 늘던 것을, 지문 줄은 글·상자·쪽만 저장해 55.0MB로 줄였다(국어는 5.3MB로 기준선 5.7MB보다 작다).

### 속도 (`app/main.py`, `pdf_source_frame_geometry.py`)

프로파일 결과 작성 뒤의 검수 단계가 전체 시간의 58~75%였고, 이 단계는 산출 HWPX를 바꾸지 않는다(작성 직후와 최종 파일의 해시 동일).

1. 변환 한 번에 문항 인식이 두 번 돌던 것을 한 번으로(작성기와 검수가 결과를 공유), 편집형 경로에서 쓰지 않는 쪽 래스터·PNG 생략(`recognize_pdf(render=False)`), 영어 판정용 전 쪽 재추출 제거(96책자에서 결과 동일 확인).
2. 배경 표 후보마다 전 쪽 도형을 다시 뽑던 것(국어 40쪽에서 518회)을 쪽 메모로.
3. **`quality_check="fast"`** (API 옵션, 기본값은 `"full"`): 원본 PDF와의 화면 대조 렌더만 생략한다. 결과 파일과 문항별 검수 표시는 같고, 점수 대신 "시각 일치 미검증"이 나온다. 화면에는 아직 노출하지 않았다.

## 남은 한계

- **본문과 작은 그래프·표가 섞인 상자**는 통째로 이미지가 된다. 본문 글자의 약 13%가 편집할 수 없는 이미지 안에 있다(수정 전에는 소실). 테두리와 안쪽 그림을 분리하는 그림 추출 재설계가 필요하다.
- **`1)` 형식 문항 번호**는 편집형 주 경로에서 여전히 실패한다. 작성기·검수기·검증 스크립트가 `N.`만 문항으로 본다. 간단 변환은 재구성형으로 폴백해 결과를 낸다.
- **전체 시험지를 가져와 한 번에 내보내면 지문이 문항마다 반복된다**(영어의 기존 구조와 같고, 이번에 국어·탐구로 넓어졌다). 내보내기 쪽에서 연속한 같은 지문을 한 번만 내는 처리가 필요하다.
- 같은 PDF를 다시 가져오면 본문이 달라져 중복 문항이 생긴다(이전 버전으로 가져온 문항과 내용 해시가 다르다).
- 받을 문항이 없는 지문(발췌본)은 앞 문항 본문 끝에 붙는다. 문항 없는 쪽이 중간에 끼면 지문 연결이 끊긴다. 가로선만으로 된 그림(연표)은 글만 본문에 남는다.
- 문제집·내신 변종(`※ [N~M]`, `(N~M)`, 6:4 단, 사각형으로 그린 구분선, 3단)은 사례 PDF가 없어 규칙을 넣지 않았다.
- `pdf_layout_writer.py`의 구 작성 블록은 도달 불가 상태로 남겼다(다른 브랜치와의 병합 충돌 회피). `find_tables`는 쪽당 두 번 호출된다(국어 4초).

## 진행자가 정할 것

1. **빠른 변환을 화면에 어떻게 낼 것인가.** Antigravity 평가는 "빠른 변환을 기본으로, 원본 대조는 변환 뒤 버튼으로 분리"를 권했다. 지금은 API 옵션만 있고 기본값은 정밀이다.
2. **"Gemini 수식 인식" 체크박스.** 서버는 정직하게 안내하지만 화면에는 그대로 있다. 숨길지, 네이티브 작성기에 실제로 연결할지.
3. **이 브랜치의 병합.** 기준이 `codex/premium-reorder-numbering` 끝(`50cd57c`)이다.

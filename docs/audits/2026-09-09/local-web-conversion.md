# 로컬·웹 변환 속도와 품질 점검

측정일: 2026-09-09. 최초 소스 기준 commit: `2fcfc4010c6058837f0289584d7956501870e153`. 아래는 **변경 전 기준점과 측정 중 도입된 미커밋 개발 코드의 후속 표본**을 구분한 보고서다.

## 최신 개발 코드 후속 확인: 14:05 시점

최초 20건 측정과 최적화 전체 실험은 13:59 이전 완료됐다. 최종 상태 확인에서 이 감사가 수정하지 않은 `app/pdf_layout_writer.py`의 변경(14:00:48 기록)과 새 `app/pdf_editability.py`를 발견했다. 기본 structured 경로가 이미지 overlay에서 일반 문단 재배치로 바뀌었다. 타 작업의 변경을 수정·되돌리지 않고 세 과목을 양쪽에서 1회씩 추가 측정했다.

**최신 소스의 로컬·웹 결과는 서로 동일하지만, 새 재배치 경로는 품질 보완이 필요하다.** 빠른 시간만 보고 개선 완료로 판정할 수 없다.

| --- | ---: | ---: | --- |
| 수학 12쪽 | 6.43초 | 4.30초 | 12쪽, 수식·본문의 크기와 배치 변형 |

이 후속 측정은 한 번씩이며 외부 부하가 통제되지 않았다. 웹 우열을 일반화하지 않는다. 동일한 임의 객체 ID만 정규화하면 세 쌍의 패키지 본문·수식·이미지·배치는 모두 동일했다. 원본 문항 개수 30/45/20도 유지되지만 **개수 보존이 문항 내용 보존을 보증하지 않는다.**

- 수학: 텍스트 보존 지표 **89.72%**, 감지 수식 구간 대비 native coverage **81.11%**, 미복원 placeholder **5개**, 내부 점수 **85.71/98**. 표본 첫 쪽에서 수식 글자가 작고 촘촘하며 원본 타이포그래피가 유지되지 않는다.
- 영어: 텍스트 보존 지표 99.73%, 내부 점수 79.99/98. 원본 8쪽이 16쪽으로 늘었고 렌더러가 다수의 본문/그림 overflow를 보고했다. 첫 쪽 하단 그림 잘림도 확인했다. 단순히 재배치로 쪽수가 바뀐 것과 이 잘림 문제를 구분해야 한다.
- 한국사: 내부 텍스트 지표 100%, 내부 점수 100/98이지만, 출력 2쪽의 **7번 지문·보기와 8번 자료 지문이 사라지고 일부 표의 글자만 남는 현상**을 원본과 대조해 확인했다. 이 내부 지표는 이미 인식된 fragment 기준이어서 원본의 모든 의미 있는 내용을 검증하지 못한다. 높은 자체 점수로 이 누락을 덮어서는 안 된다.
- 세 과목 모두 기본 API에서 시각 검수를 생략한다. 따라서 큰 속도 상승에는 overlay 생성 제거와 검사 범위 변경이 함께 들어 있다. 아래의 **출력 보존형 필터 최적화**와 다른 변경이다.

현재 우선순위는 새 재배치 경로의 지문·보기 누락, 수식 복원, overflow를 먼저 해결하는 것이다. 원본 외형을 보존하는 기존 경로를 계속 사용할 경우에는 아래 검수 필터 최적화를 적용할 여지가 확인됐다.

후속 증거: `data/local_web_benchmark/20260909_1405_reflow/`의 `results.json`, `observed_writer_diff.patch`, `source_fingerprints_post_measurement.json`, 과목별 `engine_report.json`, `filter_experiment/`. 초기 벤치마크 이후의 변경이므로 같은 HEAD의 동일 옵션 성능으로 합산하지 않는다. 재현 도구에는 향후 동시 소스 변경을 확인하도록 작업 전후 주요 파일 SHA-256도 기록하게 했다.

설치 EXE는 9월 7일 빌드다. 최신 소스 로컬 worker와 설치 EXE는 구분해야 한다. EXE는 아래 TXT 실행 표본만 확인했으며 **최신 웹과 설치 EXE의 PDF 품질이 같다는 보장은 하지 않는다.**

## 변경 전 기준점 결론

변경 전 기본 옵션에서는 로컬·웹이 같은 결과를 만들었다. 5개 변환 조합 × 2경로 × 2회, 총 20건이 모두 변환에 성공했으며, 양쪽 결과를 비교한 10쌍 모두 임의 객체 ID를 제외한 본문·수식·이미지·스타일·배치 데이터가 동일했다. 수학의 큰 병목은 PDF 문항 인식보다 전체 시각 검수였다. **검수 필터의 동등 계산 실험에서 12쪽 검수가 145.66초→8.46초(94.2% 단축)로 줄었고 페이지별 지표·판정은 모두 같았다.** 이 감사는 필터 최적화를 제품 코드에 반영하지 않았다.

문항/쪽수 보존과 원본 배치는 양호하지만, 글자가 원본보다 옅어지는 현상과 한국사 자료 상자 밖 글자 잔상을 표본 화면에서 확인했다. 높은 자동 점수를 실제 편집·인쇄 완성도로 표현하지 않는다.

수학 4회 전체에서 문항 인식은 0.26–0.31초, writer는 30.29–41.45초, 시각 비교는 145.66–209.08초, API 구조 검사는 10.69–12.24초였다. 인식 시간은 writer 안에, 실제 HWPX 렌더 시간은 시각 비교 안에 포함되어 중복 합산하면 안 된다. 수학 전체 시간의 약 76–79%를 시각 비교가 사용했다.

### 실제 실행기/웹 대기열 표본

같은 TXT를 추가로 3회씩 처리했다. 배포 폴더의 `dist/HWP-Make-Basic/HWP-Make-Basic.exe --worker`는 **2.92 / 0.98 / 0.99초**, 실제 웹 접수→대기열→worker→다운로드는 **2.69 / 2.58 / 2.59초**였다. 원본 소스 버전의 결과와 모두 동일했다.

웹 표본은 FastAPI ASGI TestClient로 실제 Store/Worker를 실행한 결과다. HTTP 업로드 로직·파일 저장·대기열·별도 변환 프로세스·다운로드 로직은 포함하지만 인터넷·소켓·브라우저 2.5초 폴링은 제외한다. 설치 EXE 표본은 TXT만 대상으로 하며 PDF 전체 성능을 EXE까지 재측정했다고 주장하지 않는다. 증거는 `entrypoint_probe/results.json`이다.

## 변경 전 기준점의 측정 범위

- 같은 Windows PC, Python 3.14.3에서 현재 `app.desktop_convert.convert`와 `app.web_convert.convert`를 실행했다. 매 작업은 새 자식 프로세스와 독립 엔진 DB를 사용한다.
- 고1 2026년 6월 수학 12쪽·영어 8쪽·한국사 4쪽 실물 PDF와 2문항 합성 TXT를 사용한다. PDF는 HWPX, TXT는 HWPX와 DOCX로 변환한다.
- `structured`, `native_math=True`, AI off, `variant_policy=all` 조건이다. 각 경로 2회, 첫 회는 로컬→웹, 두 번째는 웹→로컬 순서이며 변환 작업은 직렬 실행한다.
- 시간은 자식 프로세스 시작부터 종료까지다. 실제 변환 함수와 내부 검증을 포함하며 단계 관측용 JSON 기록·리포트 보존 비용도 포함한다. 웹의 인터넷 전송·접수 대기열·브라우저 갱신·다운로드, 설치 EXE의 시작 비용은 별도다. OS 파일 캐시와 다른 사용자 프로그램 부하는 통제하지 않았다.
- 기존 사용자 DB와 변환 결과를 변경하지 않았다. 이번 추가 파일은 벤치마크·실험 도구와 감사 문서이며 제품 엔진의 실행 동작은 변경하지 않았다.

## 변경 전 경로 차이

PDF→HWPX 기본 변환은 양쪽 모두 `main.export_pdf_layout`을 호출한다. 웹이 `native_math`를 생략하지만 모델 기본값이 True여서 설치형 로컬의 명시적 True와 같다. 일반 파일은 로컬이 `main.import_file` 검증 래퍼를 거치고 웹이 importer를 직접 호출한다. 기본 양식·원번호 보존·네이티브 수식 옵션은 같다.

로컬 브라우저의 **간단 변환**도 같은 structured 경로다. 반면 스튜디오 **원본 레이아웃** 버튼은 coordinate 모드를 사용하며 AI 인식을 선택할 수도 있다. 이 두 설정을 혼합해서 로컬·웹 품질 차이라고 해석하면 안 된다. 상주 로컬 서버는 매 파일 약 1초 수준의 엔진 import 비용도 반복하지 않는다.

| 항목 | 설치형 로컬 Basic | 웹 프로토타입 |
| --- | --- | --- |
| 파일 제한 | 64MB | 20MB, PDF 1–50쪽 |
| 추가 작업 대기 | 현재 앱 작업 | 전체 변환 1개씩 처리, 앞 작업만큼 대기 |

웹의 유휴 상태에서 위 세 폴링만으로 약 0–4초가 추가될 수 있다. 혼잡 대기와 네트워크 시간은 이 범위에 포함하지 않는다. 1초짜리 TXT 작업에는 이 비용이 크게 느껴지고, 수분짜리 수학에서는 공통 엔진 검수가 더 큰 병목이다.

## 품질 판정의 의미

- 원본 문항 수는 이번 세 실물 샘플의 30·45·20문항 기준이다. 엔진이 스스로 출력한 인식 개수만으로 임의의 새 문서까지 정확하다고 판정하지 않는다.
- `editable_text_coverage_ratio`는 편집 텍스트 보존 지표다. 수식 의미의 정답률이나 실제 편집 편의성 점수가 아니다.
- 네이티브 수식 객체 수/감지된 수식 구간 수가 100%여도 모든 분수·근호·첨자의 수학적 의미가 완벽히 복원됐다는 뜻은 아니다.
- 현재 출력은 편집 텍스트/수식 위에 원본 영역 이미지를 겹쳐 외형을 보존한다. 수학은 이미지 480개(수식 overlay 294, 텍스트 overlay 180 포함), 영어 185개, 한국사 98개이며 전체 페이지 이미지 수는 모두 0이다. 이미지 수 전체를 복원 실패 수로 세지 않는다.
- 수학 12쪽은 패키지 검사와 editor-open safety 검사를 통과했다. 독립 수식 높이 검사에서는 수식 199개, 문단/셀 높이 부족 0이지만 `figure_not_safe_inline` 관련 그림 배치 경고 417건이 남았다. 좌표형 그림을 inline 전용 기준으로 검사하는 기존 불일치가 포함되므로 이를 실제 수식 잘림 417건으로도, 전체 안전성 PASS로도 표현하지 않는다.
- 실제 한글/Word에서 내용 수정 후 재배치·인쇄한 결과, 스캔 OCR, HWP/HWPX/DOCX 입력 및 새 출판사 문서의 전반적 정확도는 이번 재측정 범위 밖이다.

## 변경 전에도 존재한 품질 측정 공백

`main._export_pdf_layout`은 `structured_math_visual_overlay`에 대해서만 structured 예외로 시각 비교를 수행한다. 영어·한국사의 실제 모드는 `structured_text_visual_overlay`인데도 순수 reflow처럼 처리해 비교를 건너뛴다. 따라서 두 과목의 API 리포트에는 렌더 출력 쪽수와 종합 점수가 없고, 안내 사유도 실제 모드와 맞지 않는다. 이번 감사는 이 경로의 출력도 별도로 렌더해 확인한다.

이 공백 때문에 영어·한국사가 수학보다 빠른 이유 일부는 검수 범위 차이다. 두 과목의 빈 점수를 0점이나 100점으로 해석하지 않는다. 빠른 동등 계산 검증 후 세 과목의 시각 검수 정책을 맞추는 것이 후속 과제다.

## 최적화 실험 결과

실험은 `scripts/probe_fidelity_filter_speed.py`에서 Pillow L 모드 MaxFilter 호출만 NumPy 가로/세로 최대값 계산으로 대체한다. 1×1을 포함한 작은 크기·좁은 이미지·임의 회색조·이진 마스크와 3/5/7/9/15/17/21 커널 조합 **56건에서 원본 필터와 픽셀 단위 일치**를 확인했다. RGB 보정 필터는 그대로 둔다.

| 확인 | 결과 |
| --- | --- |
| 수학 기존 전체 검수 → 실험 전체 검수 | 145.66초 → 8.46초, 17.2배, 94.2% 단축 |
| 수학 페이지별 지표/기본 판정 비교 | 12쪽 모든 필드 일치, review flag 동일 |
| 영어 추가 전체 검수 | 8쪽, 6.16초 |
| 한국사 추가 전체 검수 | 4쪽, 3.24초 |
| 최적화 적용 수학 전체 worker 실험 | 24.76초, 1회 |
| 전체 worker 결과 검증 | 본문/수식/그림/배치 동일, stats 차이 0, quality 딕셔너리 동일 |

**전체 24.76초를 고정적인 제품 속도나 87% 개선 보장으로 해석하면 안 된다.** 필터와 무관한 writer도 직전 30.29초→13.08초, 구조 검사도 12.24초→4.19초로 달라져 실행 환경 변화가 포함됐다. 직전 로컬 전체 196.33초에서 시각 검수 152.06초만 8.46초로 교체하는 단순 계산은 약 **52.73초(73.1% 단축)**다. 이것도 다른 단계가 동일하다는 가정의 예상치이며 새 실측값이 아니다.

추가로 동일한 수학 1쪽 PNG 쌍을 같은 프로세스에서 기존→최적화→최적화→기존 순서로 계산해 환경 변화 영향을 좁혔다. **6.92초→0.49초→0.53초→5.55초**였고 모든 지표가 일치했다. 원시 결과는 `filter_experiment/filter_microbenchmark.json`에 보존한다. 실험 출력 이미지는 동일 HWPX에서 렌더한 것이며 원본을 결과물로 대체하지 않았다.

제품 반영 시에는 전역 Pillow monkeypatch를 옮기지 않고 `pdf_layout_fidelity`의 필요한 필터 호출에 한정된 helper로 구현하는 편이 적절하다. 렌더 정책을 생략하거나 품질 문턱을 낮출 필요가 없는 개선 후보다.

## 속도 개선 우선순위

1. **시각 비교 필터 최적화.** `pdf_layout_fidelity._page_metrics`는 각 페이지에서 3·7·9·15·17·21 크기의 최대값 필터를 원본·결과 마스크에 반복 적용하고 각 후보의 기하 지표까지 계산한다. 같은 사각형 최대값을 가로→세로 계산으로 분리하는 실험을 별도 프로세스에서 검증했다. 출력 문서·해상도·임계값·검사 페이지를 줄이지 않는 후보다.
2. **writer의 반복 이미지 처리/검사 비용 측정.** PDF 영역마다 rasterize→PNG encode→decode→보정→PNG encode가 반복된다. 페이지 display list 재사용과 메모리상 이미지 보정 후 한 번 저장이 후보지만, 이번 단계에서는 정확한 단축률을 보장하지 않는다. 내부 저장 검증과 API 재검증도 중복 파싱 비용을 확인한 뒤 다룬다.
3. **짧은 작업의 웹 완료 알림 개선.** 접수 시 worker 깨우기, 실행 중에만 빠른 상태 갱신 또는 이벤트 알림을 적용하면 작은 파일의 체감 대기를 줄일 수 있다. 검사 엔진의 수분 단위 지연을 이 변경만으로 해결할 수는 없다.
4. **동시 처리량 개선은 별도 부하 시험.** 작업별 프로세스 격리를 유지하면서 동시 실행 수를 조정할 수 있지만 CPU·메모리·디스크와 취소·임대 정책을 함께 시험해야 한다. 처리 수를 늘리는 것을 단일 파일 변환 속도 향상과 혼동하지 않는다.

예전 `subject_conversion_performance_2026_07.md`의 6과목 합계 20.494초는 `write_pdf_flow_hwpx` 직접 호출 기록이다. 지금 기본 structured overlay 변환과 전체 시각 검수 시간의 비교 기준으로 사용하지 않는다.

## 재현과 증거

```powershell
python scripts/benchmark_local_web_conversion.py --runs 2
python scripts/probe_fidelity_filter_speed.py --baseline data/local_web_benchmark/20260909_134020
```

원본 SHA-256, 개별 소요시간·단계시간·패키지 비교는 `data/local_web_benchmark/20260909_134020/results.json`에 기록한다. 실제 PDF와 HWPX, 이미지, 원시 리포트는 git에서 제외된 같은 디렉터리에 보관한다. `content_comparisons_run1.json`은 임의 객체 ID만 정규화한 패키지 전체 비교, `math_height_check.json`은 별도 높이 검사 결과다.

추가 도구의 Ruff 검사와 컴파일을 통과했고 이 감사의 문서 변경에 대해 `git diff --check`를 확인했다. 전체 제품 회귀 관문은 재실행하지 않았고, 이 감사는 제품 소스를 수정하지 않았다. 공유 작업 폴더에서 발견한 타 작업의 미커밋 변경은 그대로 두었다. 이번 검증을 범용 변환 엔진의 전체 회귀 PASS나 출시 승인으로 확대하지 않는다.

# 프리미엄 문항 편집·번호 연동 확장 검토

검토일: 2026-09-07 · 브랜치: `codex/premium-reorder-numbering`

후속 제품 방향: 사용자가 고급 편집을 기본 UI에서 분리된 프리미엄 기능으로 지정했다. 화면 위치·유료 경계·새 시험지 기본값·출시 단계는 [프리미엄 스튜디오 심화 기획](premium_studio_product_plan.md)을 우선한다. 아래 내용은 기술 가능 여부 검토 기록이다.

## 결론과 이번 작업 범위

**문제 순서 변경과 출력 번호 동시 변경은 확장 가능하다.** 현재 스튜디오에는 순서 이동과 개별 번호 수정이 있지만, 이동 순서에 맞춰 출력 번호를 자동 부여하는 옵션은 없다. 일반 텍스트 문항의 복사본에 번호를 부여하면 기존 HWPX·DOCX writer와 정답·해설 생성기를 함께 사용할 수 있음을 실행 검증했다.

이번 변경은 가능 여부 검토 문서와 재현용 probe다. 실제 화면·API의 자동 재번호, 프리미엄 권한, 결제는 구현하지 않았다. 가격·결제 사업자·배포도 결정하지 않았다. 기존 `README.md` 수정과 미추적 `web_service_plan.md`는 그대로 보존했다.

## 현재 기능과 확장 범위

| 항목 | 현재 상태 | 확장에 필요한 작업 |
| --- | --- | --- |
| 문제 순서 편집 | 스튜디오에서 드래그·위아래 버튼·키보드 이동 지원 | 유지. 모바일 터치 드래그는 별도 확인 |
| 개별 문제 번호 수정 | 편집기의 `editNumber`가 문제은행의 `number`를 수정 | 시험지별 출력 번호와 문제은행 원번호를 분리 |
| 이동 후 자동 재번호 | 미구현. UI의 `index + 1` 순번과 출력 원번호가 다를 수 있음 | 원번호 유지 / 연속 번호 / 시작 번호 옵션 |
| 본문·정답표·해설 번호 연동 | 모두 전달받은 `number`를 우선 사용 | 동일한 내보내기 스냅샷을 세 경로에 전달 |
| HWPX 렌더 미리보기 | 별도 `/api/preview`에서 같은 HWPX writer 사용 | 내보내기와 같은 번호 해석 함수를 사용 |
| DOCX 미리보기 | HWPX 기준으로 제공 | 실제 DOCX 렌더와 동일하다고 표시하지 않음 |
| 프리미엄 권한·결제 | 현재 앱에서 미구현 | 로그인·소유권·권한 저장·결제 상태 반영·서버 검사 |

근거:

- `static/app.js`: `renderBasket`, `moveBasketItem`, `exportSelected`, `previewExport`, `editNumber` 저장 흐름.
- `app/main.py`: `ExportPayload`, `_selected_problems_or_409`, `/api/export`, `/api/preview`. 번호 정책 필드가 없고 중복 문항 ID는 400으로 거절한다.
- `app/storage.py`: `get_problems_by_ids`는 요청 ID 순서를 유지한다. `number`는 문제은행에 저장되는 문자열이다.
- `app/hwpx_writer_v2.py`, `app/docx_writer.py`: 본문에 `problem.get("number") or str(index)` 적용.
- `app/exam_templates.py`: `quick_answer_lines`, `explanation_entries`도 같은 번호 규칙 사용.
- `app/preview.py`: HWPX v2 writer로 실제 미리보기 파일 생성.

## 첫 구현 묶음 제안

편집 가능한 일반 문항을 대상으로 **순서 이동 → 출력 번호 즉시 갱신 → 미리보기 → HWPX/DOCX 생성**을 먼저 완성한다.

1. 프리미엄 전용 시험지 구성 옵션에 `원번호 유지`와 `순서대로 번호 매기기`, 시작 번호를 추가한다. 새 프리미엄 시험지는 연속 번호 1부터, 기존 저장 시험지는 저장된 설정을 복원한다는 후속 기획을 따른다. 기본 변환은 기존 원번호를 유지한다. 순서 카드에는 원번호와 출력 번호를 구분해 표시한다.
2. `ExportPayload`에 `numbering_mode: preserve | sequential`, `start_number`를 추가한다. 예시 계약은 시작 번호 1~999, 마지막 번호도 999 이하로 제한하고 클라이언트·서버에서 동일하게 검증하는 것이다. 기존 문항 접두사 처리 범위와 함께 확정해야 한다.
3. 서버 공통 함수에서 선택 문항을 복사하고 출력 번호를 계산한다. 문제은행의 `number`를 덮어쓰지 않는다. `/api/export`와 `/api/preview`가 같은 함수와 옵션을 사용하게 한다.
4. 내보내기 접수 시 순서·원번호·출력 번호·내용을 고정한다. 유료 웹 버전에서는 이 스냅샷을 작업 DB에 저장해 새로고침·재시도에서도 동일하게 재현한다.
5. 같은 번호 목록을 본문·정답표·해설에 전달하고, 화면 예상 배치도 출력 번호를 사용해 다시 계산한다. 간단 변환의 옵션은 숨겨진 스튜디오 설정을 읽지 않게 유지한다.

예: 원본 12번과 27번을 `27 → 12` 순서로 구성하면 원번호 모드는 `27, 12`, 연속 번호 모드는 `1, 2`, 시작 번호 41 모드는 `41, 42`로 출력한다. 정답과 해설은 해당 문항을 따라 이동한다. 선지의 ①~⑤ 번호는 문제 순서 변경과 별개다.

## 별도 처리가 필요한 입력

| 입력·상황 | 단순 `number` 변경의 한계 | 처리 방향 |
| --- | --- | --- |
| 본문에 `27. 질문`이 남은 문항 | DOCX 접두사 제거는 기존 번호와 label이 같을 때만 작동해 재번호 후 중복 표기 가능 | 원번호와 일치하는 인식된 접두사만 복사본에서 제거. 소수·수식의 숫자는 일괄 치환하지 않음 |
| 공유 지문 `[1~3]` | `problem_type=passage` 구분은 있으나 DB에 명시적인 지문-문항 그룹 관계가 없음 | 그룹 ID·소속 문항을 모델링하고 지문과 묶어서 이동. 지문은 번호 카운트와 정답표에서 제외하고 범위는 소속 문항으로 계산 |
| 이어지는 지문·문항 | HWPX의 continuation 경로는 일반 번호 heading을 건너뜀 | 조각을 하나의 문항으로 묶고 시작 조각에만 번호 부여 |
| 이미지에 찍힌 원번호 | HWPX 이미지 전용 경로는 heading을 만들지 않고 이미지 자체를 출력 | 번호 영역 인식·분리·검수 전에는 자동 재번호 지원 대상에서 제외하거나 해당 문항을 수정하도록 안내 |
| PDF 원본 좌표·source text flow | `/api/pdf-layout-export`에는 선택 ID나 번호 정책이 없고, 원문 텍스트·좌표 유지 경로는 별도임 | 문항 가져오기 후 편집 경로로 전환. 원본 고정 배치의 자유 재정렬은 별도 개발 |
| 본문·해설의 “앞의 12번” 참조 | 자유 텍스트는 번호 필드와 연동되지 않음 | 구조화된 참조를 도입하거나 검수 대상으로 표시 |
| 임의 번호·중복 원번호 | 원번호는 문자열이며 서로 다른 시험지에 같은 번호가 있을 수 있음 | 연속 번호로 해소 가능. 임의 번호 편집은 시험지 항목별 매핑·중복 정책 추가 후 확장 |
| 동일 문제 여러 번 삽입 | 현재 API는 중복 ID를 거절 | 별도 시험지 항목 ID를 도입해야 하므로 첫 구현 범위에서 제외 |

일반 문항의 재번호 가능 여부를 모든 PDF·이미지·공유 지문에 대한 지원 보장으로 확대하지 않는다.

## 프리미엄 제품과 결제 기반

후속 제품 방향은 기본 변환을 유지하고, 시험지별 순서·출력 번호 편집, 구성 저장·복원, 정답·해설 동기화를 별도 프리미엄 스튜디오로 제공하는 것이다. 기본 UI에는 이 편집 도구를 추가하지 않는다. 기존 로컬 스튜디오의 순서 이동을 이미 유료 기능으로 구현한 상태는 아니다. 웹 제품의 분리와 권한 정책은 심화 기획에서 정의한다.

웹 과금 기반은 기존 [웹 서비스 전환 기획](web_service_plan.md)의 로그인·내 자료 보호·작업 대기열 이후에 붙인다. 현재 `app/main.py`는 uploads/exports를 정적으로 공개하며, 사용자 소유권이나 서버의 유료 권한 검사가 없다.

- 사용자 ID에 연결된 플랜·권한·유효 기간을 서버에 저장한다. 브라우저의 프리미엄 토글이나 요청의 `is_paid` 값으로 접근을 허용하지 않는다.
- 주문·결제·이용 권한을 구분해 저장하고 서버에서 확인한 결제 상태로만 권한을 갱신한다. 결제 완료 화면 진입만으로 활성화하지 않는다.
- 결제 알림의 진위 확인, 중복·순서 역전 처리, 취소·환불·만료에 따른 권한 변경을 구현한다. 구체 API는 결제 사업자 선정 후 해당 시점 공식 문서로 검증한다.
- 유료 편집 결과의 접수·내보내기·미리보기와 과거 동기 API에도 동일한 서버 권한 정책을 적용한다. 화면만 숨겨서는 제한되지 않는다.
- 결제 확인과 작업 접수를 연결하고, 실행 중 구독 만료·작업 실패·재시도 시 권한과 사용량을 어떻게 처리할지 고정한다.

권장 개발 순서는 **일반 문항 재번호 → 예외 입력·그룹 처리 → 웹 인증·소유권·영속 작업 → 결제와 유료 권한 → 유료 사용자 흐름 검증**이다. 가격·월 구독/건별 결제·사업자 선정은 이번 기술 검토의 확정 사항이 아니다.

| `node scripts/verify_frontend_layout.js` | 통과. 순서 변경 후 예상 배치 계산 및 화면 코드 연결 검사 |

레이아웃 결과는 `data/reorder_layout_regression/report.json`에 생성된다. 이 실행에서는 rhwp의 manifest fallback 경고가 출력됐으나 검증 실패는 없었다. 과거 7월 보고서의 역방향 6쪽 수치를 이번 결과로 재사용하지 않았다.

이번 검토에는 실제 브라우저 조작, 실제 한글/Word에서의 열기·편집·저장, 실물 스캔과 공유 지문 재번호, 결제 샌드박스 검증을 포함하지 않았다. 구현 완료 조건에는 이 검증과 무료 계정의 API 직접 접근 차단, 미리보기·다운로드 번호 일치, 원본 DB 불변, 중복 결제 알림의 권한 일관성을 포함해야 한다.
